# ТЗ 1С-разработчику: HTTP-сервис загрузки заказа (расширение конфигурации)

Дата: 06.09.2026
Для кого: 1С-разработчик базы «ВОК-Регион» (КА 2 / Softvent).
Контекст: существующий внешний путь загрузки заказа — MCP Toolkit `execute_code`
с inline-BSL (`tools/as_order_loader/`). Битрикс-бот (`bitrix_bot/`) шлёт туда
JSON позиций и получает строку-результат. Нужен штатный HTTP-сервис вместо
`execute_code`: стабильнее, без MCP, с нормальным контрактом ответа.

## Цель

HTTP-сервис в **расширении конфигурации** (без правки типовой), который
принимает JSON-спецификацию заказа, создаёт документ `асСпецификацияЗаказа`
со штатным расчётом цен и возвращает номер заказа / ошибки в JSON.

Логика загрузки УЖЕ написана и проверена end-to-end (заказы №000000852,
№000000860 — 286 позиций): модуль объекта обработки `асЗагрузкаЗаказаИзJSON`
(`tools/as_order_loader/as_order_loader.bsl`), точки входа `ЗагрузитьЗаказ` /
`ЗагрузитьЗаказВернутьJSON`. HTTP-сервис — это транспортная обёртка над ней,
без дублирования логики расчёта.

## Требования

### 1. Расширение конфигурации

- Оформить как расширение (напр. `ВОКЗагрузкаЗаказаHTTP`), типовая конфигурация
  не изменяется.
- HTTP-сервисы в расширениях поддерживаются платформой 8.3.11+ — проверить
  версию платформы публикации; при необходимости согласовать обновление.

### 2. HTTP-сервис

- Имя сервиса: напр. `specorder`; корневой URL шаблона: `/vok/order`.
- Метод: **POST** только. GET/PUT/DELETE — 405.
- Публикация на веб-сервере 1С: `https://<сервер-1с>/<база>/hs/vok/order`.
- Публиковать только в локальной сети (доступен middleware бота), наружу не
  открывать.

### 3. Запрос

`Content-Type: application/json; charset=utf-8`. Тело:

```json
{
  "order_comment": "Задача Битрикс24 №42: Шипиловский — ОВ2",
  "request_id": "bitrix-task-42-msg-7",
  "positions": [
    {
      "article": "1-2-1",
      "qty": 6,
      "thickness": 0.8,
      "material": "Рулон оц.(08ПС)0.80",
      "shina": "95",
      "conn0": "6",
      "conn1": "6",
      "params": {"A0": 400, "B0": 200, "L0": 1250},
      "comment": ""
    }
  ]
}
```

- `positions` — массив позиций по существующему контракту
  (см. `tools/as_order_loader/README.md`, раздел «Контракт JSON»); ключи
  `shina`, `conn0`, `conn1` всегда присутствуют (пустая строка = не задавать).
- `order_comment` — комментарий документа; если пуст/отсутствует — прежний
  дефолт «Загрузка из JSON». Может содержать кавычки — экранировать по правилам
  строковых литералов 1С при программной вставке.
- `request_id` — опциональный ключ идемпотентности (см. п. 6).

### 4. Ответ

Успех, HTTP 200:

```json
{
  "Успех": true,
  "НомерЗаказа": "000000860",
  "Ошибки": [],
  "Предупреждения": ["Строка 1 (1-2-1): цена 0 — проверьте прайс"]
}
```

Исключение в 1С, HTTP 500:

```json
{"Успех": false, "НомерЗаказа": null, "Ошибки": ["<ОписаниеОшибки>"], "Предупреждения": []}
```

- Кодировка UTF-8, `Content-Type: application/json`.
- «Бизнес-ошибки» загрузки (не найден продукт/материал, цена 0) — это
  НЕ исключения: документ создаётся, они перечисляются в `Ошибки` /
  `Предупреждения`, `Успех` по аналогии с текущим поведением `ЗагрузитьЗаказ`.

### 5. Логика внутри

1. Прочитать тело JSON (ЧтениеJSON), извлечь `positions`, `order_comment`,
   `request_id`.
2. Вызвать существующий код загрузки (модуль обработки `асЗагрузкаЗаказаИзJSON`
   или перенесённый общий модуль расширения): создание документа, ТЧ `Товары`,
   производные размеры из `асНастройкиПродукции`, штатный расчёт цен
   (`РедактироватьВсеНаКлиенте_ДляИзмененныхВМодуле` обработки
   `асВводНовогоЗаказа`), `Записать()`.
3. Комментарий документа = `order_comment`.
4. Сформировать структуру ответа, сериализовать ЗаписьJSON.

Перенос BSL-модуля из внешней обработки в расширение: либо общий модуль
расширения с этими процедурами, либо продолжать держать внешней обработкой и
вызывать `ВнешниеОбработки.Создать(...)` из сервиса — по усмотрению
разработчика; важно НЕ дублировать логику в двух местах.

### 6. Идемпотентность (желательно)

Бот ретраит запрос при сетевом таймауте. Если заказ уже записан, а ответ
потерян, повторный вызов создаст дубликат. Вариант решения: если передан
`request_id` — искать ранее созданный документ по комментарию/реквизиту с этим
ключом и возвращать его номер вместо создания нового. Если сложно — зафиксируйте
в ответе ограничение, бот обработает на своей стороне (сейчас дублирующий
сценарий маловероятен: таймаут 280 с, заказ №000000860 на 286 позиций писался
14 с).

### 7. Безопасность и права

- Отдельная сервисная учётная запись 1С с минимально нужными правами:
  документ `асСпецификацияЗаказа` (добавление/запись), справочники
  `асПродукция`, `асМатериалы`, `асСоединениеВоздуховодов`, регистр
  `асНастройкиПродукции`, обработка `асВводНовогоЗаказа`.
- Аутентификация: предпочтительно проверка секретного ключа в заголовке
  `X-API-Key` (ключ middleware получит из конфига). Basic Auth — допустимо.
  Без ключевой проверки — только если публикация гарантированно внутри
  замкнутой сети.

### 8. Тестирование (приёмка)

Пример вызова (сервер бота будет слать аналогично):

```bash
curl -s -X POST "https://<сервер-1с>/<база>/hs/vok/order" \
  -H "Content-Type: application/json; charset=utf-8" \
  -H "X-API-Key: <ключ>" \
  -d @order_request.json
```

- Проверка на КОПИИ базы: 2–3 позиции с известными ценами → сверить номер
  заказа, S, цены с интерактивным расчётом (паритет — уже доказан для
  `execute_code`-пути, см. README загрузчика).
- Ответ при битом JSON — 500 с понятной ошибкой, без падения веб-публикации.
- Ошибки бизнес-логики (несуществующий артикул) — 200 с заполненным `Ошибки`.

## Что изменится на стороне Python (после внедрения сервиса)

> **Готовый код для сборки расширения — `tools/as_order_loader/extension/`**
> (общий модуль-дополнение с идемпотентностью, модуль HTTP-сервиса, пошаговая
> инструкция на 15 минут). ТЗ ниже — для понимания контекста и приёмки.

- `bitrix_bot/pipeline.py::load_order_to_1c` — вместо payload
  `{"code": "<BSL>"}` на `/api/execute_code` будет POST JSON-запроса из п. 3 на
  URL сервиса с заголовком `X-API-Key`.
- Конфиг: `middleware.execute_code_url` заменится на `order_service_url` +
  `order_service_key`. Объём правок — ~20 строк + 2 теста, делаем сами после
  приёмки сервиса.

## Критерии приёмки

1. POST с валидным JSON создаёт документ, номер совпадает с видимым в базе.
2. Ответы соответствуют п. 4 (UTF-8, структура полей).
3. Повторный вызов с тем же `request_id` не создаёт дубликат (если реализован п. 6).
4. Сервис недоступен без ключа извне публикации; права сервисной учётки
   не дают интерактивного входа.

# Дизайн: LLM-нормализация пропущенных строк + словарь аббревиатур

Дата: 2026-10-28
Статус: на согласовании

## Зачем

Боевой прогон «Заявки на НИИ Кукурузы» (28.10, заказ №000001440): 18 позиций
загружено (все — восстановлены LLM doc-fallback'ом из 0 детерминированных),
но 48 строк остались в «Пропущено». Анализ показал: LLM эти строки **извлекла
и якорная валидация их пропустила** — они отброшены дальше, детерминированным
`process_rows`:

- 12× «Не удалось распознать размер / тип» — детектор типа не знает
  аббревиатуру «Возд.» («Возд.оц 0.5мм 150х150 1.25»);
- 9× «Покупная позиция» — перекупное оборудование (клапаны, гибкие
  воздуховоды) — **правильно** пропущено бизнес-правилами, не трогаем;
- остальное — «Отсутствует размер», геометрия, артикулы вне списка.

Вывод: «пускать весь документ через LLM» эти строки не спасло бы — их режет
типизация после извлечения. Нужен второй шанс на уровне **строки**: LLM
переписывает отброшенное наименование в канонический вид, и строка проходит
тот же `process_rows` ещё раз.

## Цели

1. Сократить «Пропущено» за счёт строк, отброшенных по причинам
   распознавания (тип/размер/количество), а не бизнес-правил.
2. Сохранить детерминированную гарантию: LLM не может изменить количество
   и единицу строки и не может «выдумать» строку — нормализуется только то,
   что уже извлечено из документа.
3. Хорошие документы (без отброшенных строк) не получают ни задержек,
   ни LLM-вызовов.

## Не-цели

- Бизнес-правила не меняются: «Покупная позиция», blocked-артикулы (20-x),
  «Артикул не входит в разрешённый список» — не нормализуются.
- М²-агрегаты, геометрические конфликты — вне scope (v1).
- LLM-first для всех документов — рассмотрен и отклонён (дорого на каждый
  документ, регресс-риск на ГОСТ-таблицах, исходный состав пропущенных
  не меняется).

## Анти-цели

- LLM меняет количество или единицу измерения → нарушение бухгалтерской
  достоверности.
- LLM добавляет строки, которых не было в skipped → дедуп не спасёт от
  выдуманных позиций.
- Нормализация запускается при выключенном `llm.enabled` → молчаливый no-op
  допустим, ошибок нет.

## Ограничения

- Тот же бэкенд kimi-cli subprocess, тот же гейтинг `llm_enabled()`.
- Один LLM-вызов на документ (батч отброшенных строк целиком), дедлайн
  по `time.monotonic()`.
- Конфиг: новая подсекция `llm.row_fallback` (по образцу `doc_fallback`).

## Подход (выбран пользователем)

**A — LLM-нормализация skipped-строк.** Рассмотрены также B (LLM-first для
всех документов) и C (только понизить skip_threshold) — отклонены: не решают
причину отказа, дороже/рискованнее.

## Устройство

### 1. Белый список причин нормализации

Нормализуются skipped-строки по `reason` (точные литералы и префиксы из
process_specification_table.py):

- `"Отсутствует размер"` (classify_skip, :622) — **только если unit не м²/м2**
  *(решение после builder-check: classify_skip проверяет размер раньше м²,
  сметные строки иначе просочились бы сюда)*;
- `"Не удалось распознать размер / тип"` (:625).

Всё остальное (`Единица м²`, `Покупная позиция`, `Артикул ... не входит`,
геометрия, `LLM-классификация отклонена`) — без изменений.

**Убрано из whitelist** *(решение)*: `"Не удалось распознать количество"`
(:1424, :1434) — в таких строках quantity = None/0, протокол запрещает LLM
менять количество, повторный process_rows упал бы на той же проверке. Пункт
мёртвый; восстановление количества — отдельная задача, если окажется нужной.

### 2. Протокол нормализации

В `llm_document_fallback.py` (или новый модуль `llm_row_fallback.py` — решение
билдера; тянет в сторону отдельного модуля) добавить:

```python
def normalize_skipped_rows(rows: List[Dict], cfg=None, runner=None,
                           deadline=None) -> List[Dict]
```

- Вход: skipped-строки из белого списка (их сырые `name`, `size`, `unit`,
  `quantity`).
- Промпт: вернуть JSON-массив `{name, size}` — каноническое наименование
  и размер. Правила: «Возд.» → «Воздуховод оцинкованный», «Отвод/Переход/
  Врезка» оставить, размер дословно из исходного наименования, не выдумывать.
- Валидация каждой строки ответа:
  - `quantity` и `unit` берутся из ИСХОДНОЙ skipped-строки (LLM их не
    возвращает и не меняет — полей нет в протоколе);
  - новое `name` обязано сохранить ядро исходного: хотя бы один
    алфавитно-цифровой токен длиной ≥ 3 из исходного `name` (после lower)
    входит в новое `name`. Токены с цифрами считаются («150х150» — ядро
    «Возд.оц 0.5мм 150х150 1.25») *(решение после builder-check:
    буквальное «слово из букв» отбрасывало бы флагманский кейс)*.
    Защита от полной подмены строки;
  - если `size` вернула LLM — он должен встречаться в исходном `name`
    или исходном `size` (подстрока, регистронезависимо); иначе size = "".
- Выход: нормализованные строки во входном формате process_rows
  (`{name, size, unit, quantity}`).

### 3. Интеграция в пайплайн

**Отдельная функция, независимая от doc-fallback** *(решение после builder-check)*:
`run_row_fallback(success, skipped, cfg=None) -> (success, skipped, meta)` —
вызывается из `process_pdf_to_positions` (bot) и из `web_app.py` СРАЗУ ПОСЛЕ
`run_doc_fallback`, со своим гейтингом `llm_enabled() AND
row_fallback.enabled` и своим дедлайном (отдельные 180 с; worst-case
деградированный документ ~10 мин в фоновой очереди — допустимо). Так
нормализация работает и на документах, где doc-fallback не триггерился
(низкий skip_ratio, пара странных строк), и при выключенном doc_fallback.

Внутри:

1. Собрать skipped, проходящие белый список причин (см. §1).
2. Если есть — один батч-вызов нормализации.
3. Нормализованные строки прогнать через `process_rows(rows,
   run_llm_size_classify=False)`; успешные — добавить в success с
   `"llm_source": True` (тот же флаг; отчётная секция «Восстановлено LLM
   (проверить)» их покажет вместе с doc-fallback строками), повторно
   отброшенные — вернуть в skipped с ИСХОДНОЙ причиной (не причиной
   второго прогона, чтобы отчёт не путал).
4. Дедуп с существующим success по `(comment, quantity)` — как в мердже.
5. Мета своими ключами: `row_fallback_triggered`, `row_fallback_recovered`;
   сверху пересчитать `skip_ratio_post` и `escalation` (если после
   нормализации success пуст — эскалация с причиной; если не пуст —
   `escalation=None`).

**Partial warning** *(решение)*: ставится если `(meta_doc.triggered or
meta_row.row_fallback_triggered) and skip_ratio_post > threshold` —
обновить условие в `run_pipeline`.

На файле 159 нормализация получит на вход «Возд.оц…»-строки,
восстановленные doc-fallback'ом, но отброшенные типизацией.

### 4. Словарь аббревиатур (детерминированная часть)

В `detect_product_type` / `PRODUCT_TYPE_PATTERNS`
(process_specification_table.py:200-214): добавить распознавание «возд.» /
«воздух.» как воздуховода (по аналогии с существующими паттернами). Это
вылечит самый частый класс отказов без LLM вообще; LLM-нормализация остаётся
сетью для остальных вариаций. Набор аббревиатур — начать с «Возд.» по факту
инцидента, расширять по мере появления новых причин в skipped-отчётах.

### 5. Конфиг

```yaml
llm:
  row_fallback:
    enabled: true
    timeout: 180
    max_retries: 1
```

Гейтинг: `llm_enabled() AND row_fallback.enabled`. При выключенном —
 skipped проходят как сейчас, поведение не меняется.

### 6. Наблюдаемость и отчёт

- Логи: `llm_row_fallback.triggered / .recovered / .failed` со счётчиками.
- Отчёт: единый флаг `llm_source` для секции «Восстановлено LLM
  (проверить)» — doc-fallback и нормализация не различаются в списке
  *(решение)*; в текстовую сводку добавить две цифры: «Восстановлено LLM
  (документ): N» и «Нормализовано LLM (строки): M» из meta
  (`recovered` и `row_fallback_recovered`). Новых полей PipelineResult
  не требуется.

### 7. Тесты

- Unit: белый список причин — «Отсутствует размер» принимается только при
  unit не м²; «Не удалось распознать размер / тип» принимается; м²/покупка/
  blocked/геометрия/количество — отклоняются.
- Unit валидации нормализации: подмена ядра (ни одного общего токена ≥3)
  → отброс; токен с цифрами («150х150») считается ядром и принимается;
  size не из исходника → пустой; quantity/unit из исходной строки
  неизменны.
- Интеграция на fixtures: «Возд.оц 0.5мм 150х150 1.25» + qty 21 → после
  нормализации (мок runner) строка проходит process_rows как прямоугольный
  воздуховод; detect_product_type знает «возд.».
- Интеграция порядка: doc-fallback не триггерится (низкий skip_ratio), но
  строка с «размер / тип» нормализуется — row_fallback работает
  независимо.
- Регресс: существующие 416 тестов зелёные; бизнес-пропуски (перекупка,
  м², blocked) не нормализуются даже при включённом флаге.

## Оставлено билдеру

- Отдельный модуль vs расширение llm_document_fallback.
- Точный текст промпта нормализации (итерации на фикстурах).
- Расширение PRODUCT_TYPE_PATTERNS для «возд.» (форма паттерна по месту).

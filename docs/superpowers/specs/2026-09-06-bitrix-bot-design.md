# Дизайн: бот Битрикс24 для загрузки PDF-спецификаций в 1С

Дата: 2026-09-06
Статус: утверждён пользователем

## Цель

Чат-бот в задачах Битрикс24 (портал `svok-kavkaz.bitrix24.ru`, облачный), который по упоминанию забирает PDF проектной спецификации из задачи, прогоняет существующий пайплайн проекта (`api.py` → `json_positions` → `tools/as_order_loader` → MCP `execute_code`) и возвращает в чат задачи номер созданного заказа 1С (`асСпецификацияЗаказа`) с детальным отчётом.

## Принятые решения (обсуждение)

- Битрикс24: облачный. Для событий бота регистрируется локальное приложение (client_id/secret + URL middleware). Входящий вебхук используется для REST-вызовов.
- Middleware: вариант «FastAPI + очередь в процессе» на сервере завода (white IP), без Redis/отдельного воркера.
- Режим ответа: сразу статус «Принял, обрабатываю», затем итоговое сообщение (фоновая обработка).
- «Ссылка на заказ» = только номер заказа (текущий контракт загрузчика; GUID/URL 1С не возвращает).
- Триггер: reply на сообщение с PDF + @упоминание бота. Если контекст reply не пришёл в событии — fallback: первый PDF из вложений задачи; если PDF нет — бот просит приложить файл.
- Шапка заказа: комментарий = «Задача №{id}: {название}».

## Сценарий

1. Менеджер прикрепляет PDF к чату задачи, отвечает (reply) на сообщение с файлом и тегает бота.
2. Битрикс шлёт событие `OnImBotMessageAdd` на `POST /webhook/bot` middleware.
3. Middleware немедленно отвечает 200, ставит задание в очередь и пишет в чат: «Принял `<имя.pdf>`, обрабатываю…».
4. Worker скачивает PDF по REST, гоняет пайплайн, создаёт заказ в 1С через MCP `POST 127.0.0.1:6005/api/execute_code`.
5. Итоговое сообщение бота:
   - Заголовок: номер заказа (напр. `000000860`) или «Заказ НЕ создан»;
   - Сводка: `Загружено: N · Пропущено: M · Ошибок: K`;
   - Детальные списки: ✅ загруженные позиции (артикул/наименование, кол-во), ⏭ пропущенные с причиной, ❌ ошибки/предупреждения 1С;
   - Длинные списки (>~4000 симв.) уходят прикреплённым файлом (`report.json` / текстовый отчёт), в чате — сводка.

## Компоненты (новый пакет `bitrix_bot/`)

- `server.py` — FastAPI: `POST /webhook/bot` (верификация токена, быстрый 200, постановка в очередь).
- `queue.py` — очередь: in-memory + SQLite-персистентность; один воркер, последовательная обработка (1С не любит параллельные записи); до 3 ретраев с экспоненциальной паузой.
- `bitrix_client.py` — REST-обёртка: скачивание вложений (`disk`/`imdisk`), `im.message.add` (текст и файлы в чат задачи), чтение задачи (название).
- `pipeline.py` — оркестратор: `api.process_specification_file` → `json_positions.build_positions` → `tools/as_order_loader/build_execute_payload` → MCP `execute_code`. Возвращает номер заказа, позиции, skipped, ошибки.
- `report.py` — формирование итогового сообщения: сводка + списки, нарезка/вложение при превышении лимита.
- Конфигурация: секции `bitrix:` и `middleware:` в `config.yaml`; секреты (webhook URL, app secret, токен верификации) — в gitignored `bitrix.local.yaml`.

## Поток данных

```
Чат задачи (PDF + reply + @бот)
  → Bitrix24 OnImBotMessageAdd
  → POST /webhook/bot (токен)
  → [200 OK] + задание в SQLite
  → worker: скачивание PDF (REST)
  → process_specification_file → build_positions → execute_payload
  → POST 127.0.0.1:6005/api/execute_code
  → 1С: номер заказа / ошибки
  → report.py → im.message.add (текст + файлы)
```

Шапка заказа: в JSON-контракт загрузчика добавляется поле `Комментарий` («Задача №{id}: {название}») — правка `tools/as_order_loader/as_order_loader.bsl` совместно с 1С-разработчиком (отдельная задача в плане).

## Обработка ошибок

- Недоставленное событие/таймаут Битрикса — мгновенный 200; ретраи очереди до 3 раз.
- Битый PDF / 0 позиций — «не распознал позиции», прикрепляется извлечённый сырой текст.
- `Успех: false` от 1С — «Заказ не создан», список ошибок 1С, skipped-лист файлом.
- Частичная загрузка с предупреждениями — номер заказа + блок «⚠ Предупреждения 1С».
- MCP/1С недоступна — «1С недоступна, попробуйте позже», задание остаётся в очереди для повторного запуска (команда перезапуска — вне MVP).

## Развёртывание

- Запуск: `uvicorn bitrix_bot.server:app --port 8080`, systemd-юнит.
- Публичный доступ: nginx reverse proxy + домен (напр. `bot.svok-kavkaz.ru`), Let's Encrypt HTTPS (обязательно для событий Битрикса).
- Настройка Битрикса: локальное приложение (client_id/secret, URL событий), регистрация чат-бота с правами im/task/disk.
- Секреты только в `bitrix.local.yaml` (gitignored); в git не коммитить.

## Тестирование

- Юнит (pytest, моки bitrix_client и MCP): вебхук-эндпоинт, формирование отчёта (сводка/детали/нарезка), очередь (ретраи, персистентность), выбор файла по reply, fallback.
- Интеграционный: PDF из `examples/customer_projects/` через `pipeline.py` с записанным реальным JSON-ответом 1С (без живой 1С).
- Ручной приёмочный: тестовая задача в Битриксе → живой заказ в 1С (вне автотестов).

## Открытые вопросы (не блокируют реализацию)

- Придёт ли в событии упоминания контекст reply (цитируемое сообщение с file_id) — проверить на первом интеграционном прогоне; иначе fallback на первый PDF задачи.
- Точный лимит длины сообщения im (фиксировать ~4000 симв. как безопасный порог, файлом при превышении).

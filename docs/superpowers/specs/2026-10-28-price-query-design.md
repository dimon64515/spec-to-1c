# Дизайн: прайс-запрос в битрикс-боте (расчёт цены без создания заказа)

Дата: 2026-10-28. Статус: на утверждении.
Связано: `bitrix_bot/README.md`, `docs/BACKLOG.md` («Прайс-запрос в боте без создания
заказа»), `docs/ЛОГИКА_РАСЧЕТА_ЦЕН_1С.md`, спека бота `2026-09-06-bitrix-bot-design.md`.

## Намерение и зачем

Менеджер хочет быстро узнать стоимость изделия или списка изделий (например, чтобы
ответить заказчику в переписке), не создавая заказ в 1С. Сегодня единственный путь —
загрузить PDF и создать реальный заказ. Фича добавляет в того же чат-бота режим
«расчёт цены»: вход — текст или xlsx в чате задачи, выход — сводка в чате + xlsx с
расшифровкой. Боевая база 1С в этом режиме **вообще не трогается** — расчёт идёт
в тестовой базе (`KA_vok-region_test`, копия боевой).

Цена изделия в 1С — не «цена из прайса»: она требует полного расчётного контура
(площадь S с замками, производные размеры фасонки, флаги типа цены, срез регистра
`асЦеныПродукции`). Поэтому считать можно только штатным конвейером загрузки заказа
— фича его переиспользует.

## Цели

- Менеджер пишет боту список позиций свободным текстом (напр. «1-2-1 150х150х1250
  оц.0.8 — 6 шт, отвод 15-2-1 150х150 — 2 шт») или прикрепляет xlsx.
- Бот возвращает по каждой позиции: артикул, размеры, материал, S, тип цены,
  цену за изделие, сумму; внизу итого. Формат — текст в чате + xlsx с расшифровкой.
- В ответе указывается дата актуальности цен (последнее изменение регистра
  `асЦеныПродукции` в тестовой базе) — менеджер видит, насколько копия свежая.
- Бот-агент уточняет неоднозначности в диалоге (не распознан артикул, не указан
  материал, размер «150х150» без указания что есть что — вопрос только если правило
  техотдела не закрывает случай).
- Цены совпадают с тем, что получился бы в заказе, при условии свежести копии
  тестовой базы (см. «Актуальность цен»).

## Не-цели

- Обработка PDF в этом режиме (PDF → заказ, как сейчас, в боевую базу).
- Изменение существующего потока создания заказов и round-trip.
- Изменения конфигурации/HTTP-сервиса 1С (ни боевой, ни тестовой).
- Целевой «вариант A» — расчёт без записи документа — отложен, см. BACKLOG.
- Прайс-лист «на дату» (цены — срез последних, как в заказе).

## Анти-цели

- Боевая база не должна получать ни одного документа/записи от прайс-запросов.
- «Цена без заказа» не должна молча создавать в тестовой базе документ,
  похожий на рабочий заказ: каждый служебный документ помечается на удаление.
- Расхождение цен с реальным заказом без предупреждения об устаревании копии.
- Состояние диалога, которое «зависает» и портит следующие запросы менеджера.
- Трактовка любого @упоминания бота как прайс-запроса (вопросы, уточнения
  по существующим заказам — не прайс-запросы).

## Подходы (выбор сделан в брейншторме)

- **A. Расчёт в 1С без записи документа** — целевое решение, отложено (нужен
  1С-разработчик). Спайк подготовлен в `tmp/spike_price_no_order/`.
- **B. Создать заказ → прочитать цены → пометить на удаление** — выбрано.
  Первоначально планировалось на боевой базе (минусы: мусор в журнале боевой).
  **Уточнение (решение пользователя 28.10): считаем в тестовой базе** (`KA_vok-region_test`,
  копия боевой) — боевую не трогаем вообще, HTTP-сервис/транспорт заказов не меняется.
- C. Считать цены в Python по дампу регистра — отпадает: S и тип цены вне
  контура 1С посчитать нельзя.
- D. Читать цены/помечать удаление через HTTP-сервис боевой базы — отпадает:
  требует доработки модуля 1С (нет 1С-разработчика на этом этапе).

## Как это работает

### Триггер и маршрутизация

`events.parse_event` уже принимает `.xlsx` во вложениях (ищет `(.pdf", ".xlsx")`).
Новая маршрутизация (воркер очереди `server.py`):

- сообщение с **PDF** (reply или из истории) → текущий поток заказа в боевую
  базу (без изменений);
- сообщение с **xlsx** → **бот уточняет у менеджера**: «пересчитать цены или
  создать заказ из отчёта (round-trip)?» — оба сценария используют один входной
  артефакт (xlsx-отчёт), различить их автоматически ненадёжно. Ответ уходит
  в сессионное состояние (см. ниже), round-trip работает как раньше;
- сообщение с **текстом без вложений** → прайс-запрос из текста, **но только если
  из текста разобралось ≥1 правдоподобной позиции**; иначе бот спрашивает,
  что имеется в виду (не создавая ничего в 1С);
- пустое сообщение без файлов и текста → вежливый отказ с подсказкой формата.

### Ввод 1: свободный текст

Новый модуль `bitrix_bot/price_query.py`:

1. LLM-разбор текста в список сырых позиций (артикул или описание, размеры,
   количество, материал/толщина если указаны). Используется существующий
   `llm_client`; валидация против справочника артикулов (`reference/`,
   `Справочник.асПродукция`) и `config/size_notations.yaml`.
2. Достройка по правилам техотдела — та же механика, что в `json_positions.py`
   (материал по ГОСТ-таблице толщин, шина УГФ-65/95/105 по макс. размеру,
   большее число первым для воздуховодов). Переиспользуется, не дублируется.
3. Результат: строки в формате success-строк `process_rows` → `build_positions`.

### Ввод 2: xlsx

Чтение формата Excel-отчёта (лист «Загружено»: артикул, размеры, количество,
материал, толщина — механика `report_xlsx.parse_edited_report` или её часть).
Менеджер может взять отчёт любого прошлого заказа и попросить пересчитать по
текущим ценам копии. Точный маппинг колонок — за билдером.

### Агентные уточнения в диалоге

Бот одношаговый (webhook → job → ответ). Для уточнений и ответа про xlsx
добавляется сессионное состояние в sqlite-очереди (`jobs.db`, таблица
`price_sessions`): `dialog_id → {kind: price|xlsx_disambig, draft, awaiting,
created_at, ttl(30 мин)}`.

- Вопрос бота менеджеру приходит как обычное сообщение бота в чат задачи;
  **ответ — reply на сообщение бота с @упоминанием** (платформа доставляет боту
  только обращённые к нему сообщения — это же покрывает сценарий «ответ на
  вопрос про xlsx»). Фактическая схема reply-контекста сверяется на этапе
  плана по процедуре из `bitrix_bot/README.md` («Ручная сверка событий»).
- Reply на вопрос бота сливается LLM с черновиком, расчёт идёт дальше.
- Новый прайс-запрос/заказ в диалоге сбрасывает сессию; один вопрос за раз.

### Расчёт (тестовая база, MCP execute_code)

1. Позиции → `build_positions` (без изменений) → payload как в
   `tools/as_order_loader/build_execute_payload.py`, НО **без характеристик**
   (в тестовой базе тоже не плодим справочники): комментарий с маркером
   `[РАСЧЁТ ЦЕНЫ, НЕ ЗАКАЗ] <task_id>`, расчётный конвейер тот же
   (`РассчитатьВсеСтроки`), документ **записывается** (вариант B), результаты
   (S, Sclean, Slock, Цена, ЦенаЕд, Сумма, ТипЦены, Материал) собираются в JSON
   и в **том же вызове** документу ставится `ПометкаУдаления = Истина`. Один
   round-trip MCP на запрос.
2. Идемпотентность MCP-пути отсутствует (см. BACKLOG), поэтому повтор job'а
   после частичного сбоя может дать второй служебный документ. Митигация:
   распарсенные позиции кэшируются на job (retry не гоняет LLM повторно —
   исключает расхождение суммаризации), маркер в комментарии позволяет
   находить служебные документы; детали — за планом.
3. Если MCP/туннель недоступен: **нигде ничего не создаётся** — бот пишет
   «расчёт цены временно недоступен» (плюс варианта B на тестовой: отказ
   безопасен по определению).
4. Дата актуальности цен: в том же вызове читается максимум `Период` регистра
   `асЦеныПродукции` → уходит в отчёт («цены по состоянию на <дата>»).

### Ответ менеджеру

- Текст в чат: по каждой позиции артикул, размеры, материал, S, тип цены,
  цена за изделие, сумма; итого; строка «цены по состоянию на <дата копии>».
- xlsx-вложение: лист «Расчёт» (те же колонки) + лист «Пропущено/Ошибки»
  (что не разобралось и почему). Собирается через `report_xlsx`-механику
  (новый builder; формат отчёта заказа не меняется).
- Ошибки 1С (материал не найден, цена 0 по прайсу) — предупреждениями, как
  в отчёте заказа.

### Отсечение 20-*

`BLOCKED_1C_ARTICLES` (20-1/20-2/20-9 роняют Записать) применяется и здесь —
до отправки в 1С; строки уходят в «Пропущено» с той же причиной.

## Актуальность цен (процесс вне кода)

Тестовая база обновляется из боевой **периодически, вне этого проекта**
(решению пользователя 28.10: «периодическое обновление тестовой»). Код лишь
показывает дату последнего изменения цен в отчёте — честное предупреждение
вместо гарантии свежести. Вопрос регламента обновления — к техотделу/владельцу 1С.

## Ограничения и риски

- Каждый прайс-запрос = документ в тестовой базе (сразу помеченный на удаление).
  Приемлемо: база тестовая, журнал чистится.
- Расчёт зависит от туннеля MCP к тестовой базе (сейчас туннель поднимается
  вручную с ноутбука; для фичи нужен стабильный канал — вопрос эксплуатации,
  не кода). При недоступности — честный отказ, без побочных эффектов.
- Цены актуальны на дату копии; обновление — ручной/внешний процесс.
- LLM-разбор текста недетерминирован; валидация против справочников и
  уточняющие вопросы сдерживают галлюцинации, но формат текста менеджера
  может удивить — тогда бот задаст вопрос, а не молча ошибётся.

## Решения билдера (мои, можно оспорить)

- Схема `price_sessions`, протокол слияния ответа с черновиком, порог уверенности
  LLM для уточняющего вопроса.
- Маппинг колонок входного xlsx (реюз `parse_edited_report` vs лёгкий парсер).
- Промпт LLM-разбора текста.
- Имя файла-отчёта (`report_price_<task>.xlsx`).
- Формулировки сообщений бота.

## Критерии приёмки

- Текст с 3–5 позициями (включая фасонку) → цены сходные с эталоном заказа 851
  (контроль 1-2-1 150×150×1250: S=0.793, Цена=1610, ЦенаЕд≈1276.73) — прогоном
  через MCP на тестовой базе.
- xlsx из прошлого отчёта → тот же результат, что и текст с теми же позициями.
- После расчёта документ в тестовой базе помечен на удаление (проверка вручную),
  характеристики не созданы.
- В отчёте есть дата актуальности цен.
- Позиция 20-2 в запросе → в «Пропущено», расчёт остальных не падает.
- Текст без позиций (вопрос про заказ) → бот уточняет, в 1С ничего не создаётся.
- Ответ на вопрос бота (reply + @) продолжает прерванный расчёт.
- Тесты: разбор текста, сессии, payload расчёта (без характеристик), маршрутизация
  событий (PDF→заказ; текст→цена; xlsx→уточнение).

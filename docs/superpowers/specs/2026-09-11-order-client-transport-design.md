# Дизайн: order_client.py — транспорт загрузки заказов в 1С без MCP

Дата: 2026-09-11. Статус: утверждён пользователем.

## Контекст

Загрузка заказов в 1С (`асСпецификацияЗаказа`) сейчас идёт через MCP Toolkit:
Python шлёт inline-BSL на `POST /api/execute_code` (порт 6005, SSH-туннель).
Рабочий путь (заказы №000000852/860/861), но канал сырой: произвольный код в базе,
зависимость от открытого толстого клиента, хрупкий туннель, нет идемпотентности
(дубликат при ретрае, см. BACKLOG M-8).

Долгосрочная замена согласована: HTTP-сервис в расширении конфигурации 1С
(вариант D из `docs/ORDER_LOADING_ALTERNATIVES_RESEARCH.md`). ТЗ для 1С-разработчика
и готовый код расширения уже существуют (`docs/ТЗ_HTTP_СЕРВИС_ЗАГРУЗКА_ЗАКАЗА_1С.md`,
`tools/as_order_loader/extension/`).

## Принятые решения (2026-09-11)

1. **1С-сторону делает 1С-разработчик** по готовому ТЗ и коду. Писать логику
   с нуля ему не нужно — только собрать расширение по инструкции и опубликовать.
2. **Скоуп этой задачи — только транспорт**: новый модуль `order_client.py`.
   Ни один существующий файл не редактируется. Интеграция в `bitrix_bot/pipeline.py`
   и `web_app.py` — отдельная задача после приёмки сервиса.
3. **MCP-канал после перехода:** новый сервис — основной путь, `execute_code`
   остаётся аварийным фолбэком на переходный период (переключение — в задаче
   интеграции).
4. **Приёмка — с полным покрытием позиций** (все корпуса проектов + синтетика
   по каждому из 287 артикулов справочника), чтобы не возвращаться к доработкам
   на стороне 1С.

## Скоуп

**Входит:**
- Новый файл `order_client.py` в корне репо.
- Новый файл `tests/test_order_client.py`.
- Текст узкой задачи для 1С-разработчика (раздел ниже).

**Не входит (отдельные задачи после приёмки сервиса):**
- Интеграция `order_client` в `bitrix_bot/pipeline.py::load_order_to_1c` и
  `web_app.py` (recreate round-trip).
- Прокидывание `request_id` из `bitrix_bot.queue.Job.id` (стабилен между
  reschedule) и md5-контента отчёта для recreate.
- Конфиг-переключатель транспорта и вывод execute_code из эксплуатации.

## Контракт `order_client.py`

Зависимости: только `httpx` (уже в проекте). Не импортирует `bitrix_bot`
(избегаем цикличности при будущей интеграции); для execute_code-пути импортирует
`tools.as_order_loader.build_execute_payload` (прецедент — тот же импорт уже есть
в `pipeline.py`).

```python
def load_order(
    positions: list[dict],        # контракт позиций без изменений
                                  # (article/qty/thickness/material/shina/conn0/conn1/params/comment)
    url: str,                     # "https://<1С>/<база>/hs/vok/order"  или  ".../api/execute_code"
    order_comment: str,
    request_id: str | None = None,   # сейчас не прокидывается (интеграция позже); из скриптов/тестов можно
    api_key: str = "",               # X-API-Key для HTTP-сервиса
    timeout: float = 280.0,
) -> dict:
    # {"success": bool, "order_number": str|None, "errors": [str], "warnings": [str]}
    # — та же форма, что сейчас возвращает parse_1c_result, для замены 1:1 в будущей интеграции.

def transport_for(url: str, api_key: str = "") -> HttpServiceTransport | ExecuteCodeTransport
    # auto-detect: путь содержит "/hs/" → HttpServiceTransport,
    # содержит "/api/execute_code" → ExecuteCodeTransport; иначе ValueError.
```

**Состав модуля:**
- `HttpServiceTransport` — POST JSON `{order_comment, request_id, positions}`,
  заголовки `Content-Type: application/json; charset=utf-8` и `X-API-Key`
  (п. 3–4 ТЗ HTTP-сервиса). Ответ 200 парсится той же логикой, что и сейчас
  (`parse_1c_result`-эквивалент внутри модуля).
- `ExecuteCodeTransport` — перенос текущего тела `load_order_to_1c`:
  `build_payload` + разбор двух envelope (`{"success"/"data"}` нативный HTTP-API
  и `{"result": ...}` MCP-прокси туннеля). Служит референсом и будущим фолбэком.
- Разбор результата (`Успех/НомерЗаказа/Ошибки/Предупреждения` из JSON-строки
  или dict) реализован внутри модуля; унификация с `bitrix_bot.pipeline.parse_1c_result`
  — в задаче интеграции.

## Обработка ошибок

| Ситуация | Поведение | Примечание |
|---|---|---|
| HTTP 200, `Успех=false` или непустые `Ошибки` | возврат результата-значения, без исключения | как сейчас — уходит в отчёт |
| Сетевой сбой, таймаут, HTTP 5xx | `httpx.HTTPError` | как сейчас — бот ретраит |
| HTTP 4xx (401/403/405/…) | `RuntimeError` с телом ответа | детерминированная ошибка конфигурации, ретрай бессмысленен (улучшение: текущий `raise_for_status` ретраит всё подряд) |
| Битый JSON в ответе | `RuntimeError` с фрагментом тела | диагностика, не ретрай |

## Тестирование

`tests/test_order_client.py`, стиль — как `tests/test_bitrix_pipeline.py`
(httpx MockTransport, без живой 1С):

- 200 успех → `success=true`, номер заказа.
- 200 с непустыми `Ошибки`/`Предупреждения` → `success=false` без исключения.
- 500 со структурой из ТЗ → `success=false`; 401/405 → `RuntimeError`; таймаут → `httpx.HTTPError`.
- `X-API-Key` в заголовке; `request_id` в теле запроса.
- `transport_for`: auto-detect по форме URL; неизвестный URL → `ValueError`.
- Паритет поведения двух транспортов на одном наборе позиций
  (одинаковый `dict`-результат).

**Полное покрытие артикулов** (чтобы не переделывать 1С):
- Фикстура собирает позиции из всех корпусов: Шипиловский (весь, без
  заблокированных 20-2 — см. `BLOCKED_1C_ARTICLES` в `bitrix_bot/pipeline.py`),
  Владикавказ, тренировочные наборы (`examples/для обучения 03.09.26/`,
  `05.09/`, `08.09/`).
- Плюс синтетические по одной позиции на каждый из 287 артикулов справочника
  `асПродукция` (минимально валидные размеры из метаданных `reference/`),
  чтобы покрытие не зависело от случайностей проектов.
- Контрактная проверка: каждая позиция сериализуется в валидное тело запроса
  (без живой базы). Корпус позиций генерируется один раз скриптом
  (PDF-пайплайн по корпусам + синтетика по справочнику) и коммитится как файл
  в `tests/fixtures/`; тесты только читают файл, пайплайн в рантайме тестов
  не гоняют.

## Живая приёмка (чек-лист, после того как программист поднимет сервис)

Выполняется вручную на копии базы (по готовности сервиса, отдельно от этой задачи):

1. Все собранные позиции (корпуса + синтетика) загрузить через новый сервис.
2. По каждой позиции сверить с эталоном (заказы №000000853–861): продукт,
   размеры, шина, материал, S, масса, тип цены, цена, сумма.
3. Нулевые расхождения → сервис принят → задача интеграции в бота.
4. Smoke repeat: повторный вызов с тем же `request_id` → тот же номер, дубликата нет
   (если программист оставил идемпотентность из `ДополнениеHTTP.bsl`).

## Задача программисту 1С (узкая, к передаче)

> Собрать расширение `ВОКЗагрузкаЗаказаHTTP` строго по инструкции
> `tools/as_order_loader/extension/README.md` (~15 минут в конфигураторе).
> Весь код готов: `as_order_loader.bsl` (логика загрузки и расчёта цен,
> проверена end-to-end на заказах 852/860/861) + `ДополнениеHTTP.bsl`
> (вход `ЗагрузитьЗаказHTTP` с идемпотентностью по `request_id`) +
> `МодульHTTPСервиса.bsl` (обработчик POST `/vok/order`).
> Логику не писать и не менять — только транспортная обёртка.
> Опубликовать `POST /hs/vok/order` в LAN (наружу не открывать), включить
> проверку `X-API-Key`. Идемпотентность по `request_id` — не вырезать.
> Результат: URL сервиса + подтверждение smoke-вызова (curl — в README инструкции).
> Детали и критерии приёмки: `docs/ТЗ_HTTP_СЕРВИС_ЗАГРУЗКА_ЗАКАЗА_1С.md`.
> Открытые технические пункты (все уже в ТЗ): платформа 8.3.11+ для
> HTTP-сервисов в расширениях; безопасный режим расширения — выкл;
> сервисная учётка / привилегированный режим.

Честная оговорка для приёмки: логика загрузчика на живой базе проверена
(через execute_code-путь), HTTP-обёртка — нет; поэтому приёмка — только
полным прогоном по чек-листу выше.

## Отложенные задачи (не часть этой спеки)

1. Интеграция `order_client` в `bitrix_bot/pipeline.py::load_order_to_1c` и
   `web_app.py` recreate; `request_id = f"bx{task_id}-job{job_id}"` (бот) и
   `"rt-" + md5(content)` (recreate).
2. Конфиг-переключатель `middleware.order_transport: auto|http_service|execute_code`
   + `order_service_url`/`order_service_key` в `bitrix.local.yaml`; auto =
   по наличию `order_service_url`.
3. После переходного периода: вывод ExecuteCodeTransport и MCP Toolkit
   из эксплуатации.

# Дизайн: LLM-fallback на уровне документа + автоэскалация

Дата: 2026-10-28
Статус: на согласовании

## Зачем

Сегодня (28.10) два документа подряд загрузили **0 строк** в 1С:

- Job 159 — «Заявка на НИИ Кукурузы Вентиляция (1).pdf»: свободная вёрстка, текстовый fallback склеил колонки (количество «залипло» в наименование, в `size` попали номера позиций). 0 из 39 строк.
- Job 160 — «525 бот.pdf»: смета в м² без поканальных размеров + перекупное оборудование. 0 из 81 строки.

Существующий LLM-fallback работает только на уровне поля «размер»
(`llm_size_classifier.py`) и **выключен на проде** (`config.yaml: llm.enabled: false`).
При полном промахе бот лишь отвечает «не распознал ни одной строки» — без попытки
спасти документ и без эскалации менеджеру. Менеджер узнаёт о проблеме случайно или не узнаёт вообще.

## Цели

1. Ни один документ не должен молча давать 0 строк: сначала LLM-разбор документа целиком, при неудаче — понятная эскалация менеджеру в чат Bitrix.
2. Запуск fallback не только при 0 строк, но и при деградации: доля skipped-строк выше порога из конфига (по умолчанию 30%).
3. LLM не сочиняет цифры: как в `llm_size_classifier.py`, модель возвращает класс/структуру и смещения подстрок (spans) в исходном тексте, числа вырезаются детерминированно.
4. Строки, восстановленные LLM, проходят через существующий `process_rows` — вся downstream-логика (ариткулы, характеристики, цены, фильтры blocked-артикулов) переиспользуется.

## Не-цели

- Не переписываем детерминированный каскад извлечения (PyMuPDF таблицы → текст → OCR). Он остаётся первым и основным.
- Не чиним справочники 1С (арматура без артикулов, материалы) — отдельные задачи из BACKLOG.
- Vision-разбор (рендеры страниц в мультимодальную модель) — отдельный этап позже, если текстовый fallback покажет недостаточную точность.

## Анти-цели (провал, даже если «работает»)

- LLM галлюцинирует позиции или количества, которых нет в документе → защита spans + валидация.
- Fallback дублирует позиции, которые детерминированный путь уже распознал → дедуп при мерже.
- Сбой LLM (таймаут, kimi-cli упал, невалидный JSON) роняет пайплайн → любой сбой fallback = возврат к детерминированному результату + пометка в отчёте.
- Fallback замедляет обработку нормальных документов → триггер строго по условию, лимиты на объём текста и время.

## Ограничения

- Бэкенд LLM — kimi-cli как subprocess (как `llm_size_classifier._run_kimi`). Конфиг: `config.yaml`, секция `llm`.
- Воркер очереди (`bitrix_bot/queue.py`) имеет свои таймауты — fallback обязан укладываться в разумное время (лимит в конфиге, по умолчанию 180 с на документ).
- На проде `llm.enabled: false` — включение fallback требует осознанного изменения конфига; по умолчанию в коде поведение без LLM не меняется.

## Подходы (рассмотрены в обсуждении)

- **A — «спасение документа» через LLM с переиспользованием пайплайна** (выбран): сырой текст PDF → LLM → JSON-строки со spans → `process_rows` → мердж с детерминированным результатом → эскалация при неудаче. Закрывает оба сегодняшних кейса.
- **B — точечный репарсинг skipped-строк**: дешевле по токенам, но не спасает м²-сметы и документы, где колонки развалились до построчного разбора. Отклонён.
- **C — Vision-разбор**: точнее для кривой вёрстки, но требует нового бэкенда. Отложен как этап 2.

## Устройство (подход A)

### 1. Триггер

В `bitrix_bot/pipeline.py` (точка — после `process_pdf_to_positions`, до формирования
`PipelineResult`) и симметрично в `process_csv`-пути:

```
skip_ratio = skipped / (skipped + success)   # при (skipped+success) > 0
триггер = (success == 0) or (skip_ratio > llm.doc_fallback.skip_threshold)
```

Из расчёта skip_ratio **исключаются** строки, отфильтрованные
`_filter_blocked_articles` (артикулы 20-1/20-2/20-9) — это известный дефект 1С,
а не сбой парсинга; документ из одних противопожарных клапанов не должен
запускать LLM впустую. *(решение агента)*

**Гейтинг** *(решение агента)*: doc_fallback активен только когда
`llm.enabled: true` И `llm.doc_fallback.enabled: true`. Выкатка кода без
изменения конфига не меняет поведение на проде.

**Скоуп путей** *(решение агента)*: fallback применяется только к PDF-путям —
бот (`run_pipeline`) и вебапп. CLI `process_csv` принимает уже табличные данные,
документный fallback там неприменим. Round-trip из исправленного отчёта
(`recreate_order_from_report`) LLM не запускает — там уже вмешался человек.

Конфиг (новая подсекция `llm.doc_fallback` в config.yaml):
`enabled: false` (по умолчанию; на проде включается осознанно вместе с
`llm.enabled`), `skip_threshold: 0.3`, `max_chars: 60000`, `timeout: 180`,
`max_retries: 1`. `timeout` — дедлайн на **всю операцию** fallback (извлечение
текста + вызов kimi + разбор ответа), контролируется по монотонным часам,
а не только `subprocess.run(timeout=...)` на отдельный вызов. *(решение агента)*

### 2. Модуль `llm_document_fallback.py` (новый, в корне)

- `extract_document_text(pdf_path) -> str` — текстовый слой PyMuPDF постранично; если слоя нет — переиспользовать OCR-инфраструктуру `pdf_spec_extractor`. Обрезка до `max_chars`.
- `parse_document_with_llm(text) -> list[LlmRow]` — промпт просит JSON-массив:
  `{name, name_span, size, size_span, unit, quantity, quantity_span}`.
  Spans — смещения в исходном тексте; числа (количество, размеры) извлекаются
  детерминированно из spans, а не из сгенерированных значений. Вызов через
  общий клиент kimi-cli (вынести `_run_kimi` из `llm_size_classifier` в общее
  место, не дублировать).
- Валидация каждой строки: spans указывают на существующие подстроки, quantity > 0,
  unit ∈ допустимого множества; невалидные строки отбрасываются с логом.
- Любое исключение/таймаут/невалидный JSON → возврат `[]` + причина в лог,
  пайплайн продолжается с детерминированным результатом.

### 3. Мердж

- LLM-строки прогоняются через `process_rows` (как обычные строки таблицы),
  но с подавленной повторной size-классификацией LLM (их размеры уже разобраны
  LLM — иначе kimi вызывался бы дважды на одном документе). *(решение агента)*
- Итог = детерминированные success ∪ LLM-success; дедуп по ключу
  (нормализованное наименование, размер, количество) — при совпадении приоритет
  у детерминированного результата.
- Мердж происходит **до** `_filter_blocked_articles` в `process_pdf_to_positions` —
  фильтр применяется и к LLM-строкам, иначе заказ может рухнуть в ПередЗаписью
  1С. *(решение агента)*
- Строки из LLM помечаются флагом `source="llm_fallback"` — попадают в отчёт
  отдельной секцией «Восстановлено LLM», чтобы менеджер видел, что проверить.

### 4. Эскалация

Два уровня сигналов менеджеру:

- **Полный промах**: после LLM-fallback `success == 0` → эскалация с причиной.
- **Частичная деградация** *(решение пользователя)*: заказ создан, но
  skip_ratio после мерджа всё ещё выше `skip_threshold` → предупреждение
  «заказ загружен частично, проверьте отчёт», без остановки процесса.

Механика:

- `PipelineResult` получает поле `escalation` с текстом причины. Причина
  формулируется детерминированно из агрегированных skipped-причин (например,
  «документ — смета в м² без поканальных размеров», «нет текстового слоя, OCR не
  дал результата», «все позиции — перекупное оборудование»).
- `bitrix_bot/server.py` отправляет менеджеру сообщение в тот же чат: причина +
  имя файла + предложение обработать вручную.
- **Транспорт** *(решение пользователя)*: известный баг
  `imbot.message.add: 400 APP_ID_ERROR` чиним в коде — переводим отправку
  сообщений (как минимум эскалацию и предупреждения) на `im.message.add` от
  имени пользователя вебхука (`bitrix_client.py`). Меняется «личность»
  отправителя в чате — принято. Починка регистрации бота на портале — вне
  этой задачи.

### 5. Включение существующего size-fallback

- `config.yaml`: `llm.enabled: true` (прод-конфиг меняется осознанно при выкатке).
- Отдельным этапом (можно в этом же плане, отдельной задачей): расширить
  `ADOPTABLE_CLASSES` в `llm_size_classifier.py` — сейчас фасонка с нестандартным
  размером всегда уходит в skipped, даже когда LLM классифицировал формат.

### 6. Наблюдаемость

- Логи: события `llm_doc_fallback.triggered / .recovered / .failed / .escalated`

- Дашборд: счётчик срабатываний fallback и эскалаций (по образцу существующих

### 7. Тесты

- Фикстуры: `tmp/bitrix_bot/159.pdf` и `160.pdf` → скопировать в `tests/fixtures/`.
- Unit: триггер (0 строк, skip-ratio выше/ниже порога), валидация spans,
  дедуп при мерже, сбой kimi-cli → деградация без падения.
- Интеграционные с моком kimi-cli: 159 даёт >0 строк после fallback;
  160 → эскалация с причиной «м²».
- Существующие 385 тестов должны остаться зелёными.

## Оставлено билдеру

- Точный текст промпта и схема JSON (итерации на фикстурах 159/160).
- Точное значение `skip_threshold` после прогона на архиве документов.
- Формат сообщения эскалации менеджеру.

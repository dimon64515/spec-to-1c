# Дизайн: веб-интерфейс заявок (загрузка, цены, подбор аналогов)

Дата: 2026-11-02. Статус: на согласовании.

## Намерение и зачем

Менеджеру нужен экран вместо ручной возни с файлами: загрузить PDF спецификации,
увидеть распознанные позиции и предложенные аналоги, загрузить заказ в 1С одной
кнопкой и увидеть цены (из 1С для производимого, дилерские — для перекупного).

## Цели

- Загрузка PDF/CSV/XLSX через браузер → прогон полного пайплайна бота (process_pdf_to_positions,
  с LLM-фолбэками и чипами escalation/LLM-восстановлено).
- Таблица заявок: история загрузок с состоянием (обработано/ошибки/escalation/LLM).
- Экран заявки: позиции с ценой ед./суммой (после загрузки в 1С), раздельно «производимое»
  и «перекупное» (дилерские цены), пропущенные с причиной и предложенным аналогом.
- Загрузка заказа в 1С из UI одной кнопкой (как в боте: build_positions → load_order_to_1c →
  merge построчных цен из ответа). До загрузки — кнопка неактивна/помечена.
- «Принять аналог» у пропущенной строки: конвертация в загруженную позицию — подбор категории
  (customer_product_mapping), артикула (product_article_mapping), повторный разбор размеров
  из текста строки; при нераспознанном размере — состояние «аналог недоступен: размер
  не распознан», строка остаётся пропущенной.
- Экспорт: XML для 1С + xlsx-отчёт (переиспользуем report_xlsx.py / generate_order_xml.py).
- Форма реквизитов заказа (customer, INN, numberOrder, numberDate, email/phone/contact)
  на экране заявки до загрузки в 1С; пустые — по умолчанию (как в process_rows).

## Не-цели

- Редактирование xlsx round-trip из UI (остаётся в Streamlit/боте).
- Аутентификация (пока — локальный/внутренний инструмент, bind на 127.0.0.1 или порт бота).
- Отправка результатов в Битрикс (боевой канал уведомлений — битрикс-бот).

## Анти-цели

- Новое хранилище сложнее sqlite. Всё — одна sqlite-база рядом с jobs.db.
- Фреймворки фронтенда (React и т.п.) — серверные страницы, минимум JS (vanilla + Chart.js там, где нужно).

## Ограничения

- Существующие чистые прослойки без Streamlit-зависимостей: api.py, process_rows,
  price_search/engine.py, report_xlsx.py, generate_order_xml.py, map_customer_equipment.py.
- Дизайн-гайд: dashboard-design-skill (abdiraimov-otabek) — слово-максимум на экране,
  цифры и формы, проблемы помечены на данных, тултипы вместо подписей, QA-скриншоты в конце.
- Питон 3.12, зависимости только из существующего venv.

## Подходы (выбран 1)

1. **FastAPI + серверные страницы (Jinja2), sqlite-хранилище заявок** — выбран.
   Один процесс/порт, тот же стек, что у бота и дашборда; хранилище — таблица
   `requests` + `positions` в sqlite. Минус: HTML на сервере, но для внутреннего
   инструмента это плюс (меньше кода, проще поддержка).
2. FastAPI + React SPA — отвергнут: двойной стек, деплой, для внутреннего инструмента избыточно.
3. Расширение Streamlit web_app.py — отвергнут: слабый контроль дизайна,
   медленно на больших таблицах, дублирование с новым интерфейсом.

## Архитектура

- Новый пакет `web_ui/`: `app.py` (FastAPI, lifespan с фоновым воркером), `store.py`
  (sqlite: requests, positions, analog_suggestions; статусы: pending/processing/done/error),
  `pipeline_runner.py` (оборачивает bitrix_bot.pipeline.process_pdf_to_positions →
  price_search для перекупного → сохранение в store), `templates/` (Jinja2: base, index — список заявок,
  request — детали), `static/` (немного CSS по гайду дашбордов).
- Upload: POST /upload (multipart) → авто-выбор страниц (_spec_candidate_pages из api.py,
  чтобы сотни страниц проекта не шли через OCR целиком) → создаёт request → фоновая задача
  (asyncio.to_thread) → редирект на /r/{id} с polling статуса (каждые 2 с, fetch) — без websockets.
- Экраны:
  - `/` — список заявок: дата, файл, число позиций, сумма, статус-чипы
    (ошибки 1С/escalation/LLM-восстановлено), сортировка по дате.
  - `/r/{id}` — форма реквизитов заказа (customer, INN, numberOrder, numberDate,
    email/phone/contact; пустые — по умолчанию, как в process_rows) + KPI-полоса
    (позиций, сумма, пропущено, перекупное), таблица позиций:
    статья, наименование, размер, кол-во, цена, сумма; раздельные секции
    «Загружено» / «Перекупное (дилерские цены)» / «Пропущено» с причиной;
    у пропущенных — предложенный аналог (категория из customer_product_mapping,
    артикул из product_article_mapping) и действие «принять аналог» — конвертация
    в загруженную позицию с повторным разбором размеров; при нераспознанном размере
    строка остаётся пропущенной со статусом «аналог недоступен: размер не распознан».
  - Кнопки: «Загрузить в 1С» (build_positions → load_order_to_1c, как в боте;
    после успеха — построчные цены мержатся из ответа), «Скачать XML», «Скачать отчёт xlsx».
- Дилерские цены: price_search AsyncPriceEngine вызывается в фоне только для перекупных позиций;
  при недоступности источников — статус «цена не найдена», тихо, без блокировки.
- Тесты: tests/test_web_ui_*.py — store (CRUD, статусы), runner (на фикстурах из tests/fixtures,
  мок api/price_search), страницы (TestClient).

## Что оставлено на усмотрение исполнителя

- Точные имена колонок sqlite, тюнинг CSS-токенов, порядок колонок таблицы.
- Обработка XLSX/CSV входа (если api.py не покрывает — только PDF).
- Вынесение ли price_search в отдельный поток (asyncio.to_thread) — по месту.

## Открытые решения (приняты мной, помечены как таковые)

- Порт по умолчанию 8092, bind 127.0.0.1 (мой выбор; при деплое за nginx поменять).
- Список аналогов — одно предложение на позицию (по маппингу), не каталог всех аналогов завода.
- Повторная загрузка в 1С после «принять аналог» — создаёт новый заказ (как round-trip у бота),
  старый удаляется вручную в 1С; UI предупреждает об этом.
- Локализация — русская, тултипы вместо подписей (по дизайн-гайду).

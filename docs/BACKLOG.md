### 1С-сторона: расхождения при импорте XML (зафиксировано 04.09.2026, заказ №000000847)

Контекст: тестовый импорт `order_test_connections_0904_small.xml` (50 позиций) в 1С Sofтвент.
Python-пайплайн передаёт в XML корректные значения (проверено разбором кода загрузки):
XML-поле `material` → тип материала, `thickness` → t/t2, `connection_N` → соединение.
Шину из XML передать **нельзя** — её выбирает код 1С. Три расхождения с правилами
техотдела (правила техотдела — в приоритете, т.к. они вбивают заказы вручную):

1. **Порог шины УГФ-65.** 1С ставит УГФ-65 при макс. стороне ≤250 мм; техотдел
   требует ≤350 («от 100 до 350 – шина 20/УГФ 65»). Зона 251–399 мм сейчас получает
   УГФ-95 вместо УГФ-65 (пример из 847: отвод 300x200, тройник 300x200, воздуховод 350x250).
   Эмпирическое правило 1С: max ≤250 → УГФ-65; 300–950 → УГФ-95; ≥1000 → УГФ-105.
   Где копать: константа `асИспользованиеШиныУГФ2065До` (=150 в базе), справочник
   соединений «УсловияНаШинаУголок» (диапазоны от_s1/до_s2), код в
   `docs/модуль загрузки с сайта.txt` строки ~14746–14781 — сравнение идёт по
   `Мин(A,B)`, для правила «по наибольшему размеру» должно быть `Макс`.
   Целевое правило: 100–350 → УГФ-65; 400–950 → УГФ-95; ≥1000 → УГФ-105.

2. **material=1 (оцинкованная) встаёт AISI 430/304.** Подбор делает
   `асОбщийМодуль.НахождениеМатериалаПоТипу(Артикул_Материала, Продукт)`
   (вызов: `модуль загрузки с сайта.txt` строка 32345). Подбор идёт по толщине,
   оцинкованные «Рулон/Лист/Штрипс оц. 0.70/0.80» в справочнике `асМатериалы` есть,
   но выбирается «Лист.нерж. (AISI 430/304)». Похоже на ошибку фильтрации по типу.
   Пример из 847: воздуховоды 1-2-1 t=0.7/0.8 → AISI 430 вместо рулона оц.
   Код модуля недоступен через MCP (read-only) — нужен 1С-разработчик.

3. **Чёрная сталь (material=3) ломается при импорте.** В XML корректно: material=3,
   t=1.5; в 1С: t=0.5 и материал пустой. Пример из 847: строка 2, 1-2-1 900x700.
   Причина на стороне парсинга/подбора в 1С (тот же модуль загрузки).

Мелочь: t=0.55 в 1С отображается как 0.6 — проверить при приёмке, возможно округление
в интерфейсе.

**Статус:** НЕ РЕШЕНО для XML-пути (ожидает доступ к коду `асОбщийМодуль` или 1С-разработчика).

**Обход на стороне Python-проекта (05.09.2026, РЕШЕНО):** прямой путь загрузки
обходит все три расхождения — шина передаётся напрямую по правилам техотдела
(`json_positions.shina_by_max_dim`), материал — точным именем справочника
(`json_positions.material_1c_name`), без подмен в 1С. Проверено end-to-end:
заказ №000000852 (12 позиций, границы 350/950 мм), заказ помечен на удаление.
Инструменты: `json_positions.py` (корень), `tools/as_order_loader/build_execute_payload.py`
(inline-BSL для `POST /api/execute_code`), `tools/as_order_loader/as_order_loader.bsl`
(EPF-версия). Пока техотдел правит XML-путь вручную, прямой путь — рабочий.

### «Оформить заказ»: «Значение поля Рабочее наименование не уникально» (05.09.2026, заказ №000000860)

Симптом: кнопка «Оформить заказ» в обработке `асВводНовогоЗаказа` падает, заказ
не оформляется. Стек из журнала регистрации: форма обработки
`ОформитьЗаказ()` → `ОформитьЗаказНаСервере_УТ()` → `Спр.Записать()`
(модуль формы, ~строка 2672) → `ПередЗаписью` справочника
`ХарактеристикиНоменклатуры`: «Значение поля "Рабочее наименование" не уникально».

Механика (воспроизведена программно): обработка при оформлении для каждой строки
генерирует имя характеристики «<обозначение>  <материал.НаименованиеДляПечати>»
(например «Ф200-200  Рулон оц.(08ПС)0.55») и создаёт элемент у владельца =
Номенклатура строки. Поиск существующей характеристики перед созданием в коде
формы НЕ находит её (хотя элемент с таким именем у того же владельца в базе есть —
проверено: точных дублей в справочнике нет, контроль уникальности БСП включён
константой `КонтролироватьУникальностьРабочегоНаименованияНоменклатурыИХарактеристик`),
идёт попытка создания дубля → штатный контроль БСП рубит запись → транзакция
оформления целиком откатывается. Падает и на строках, чья характеристика уже есть
в базе (в 860 — дроссели 16-1-1 Ф160/Ф200 t=0.55), и, вероятно, на повторах одной
позиции внутри заказа (40 дубль-ключей в Шипиловском).

**Статус:** НЕ РЕШЕНО (баг 1С-обработки; нужен 1С-разработчик — точка:
модуль формы `асВводНовогоЗаказа`, `ОформитьЗаказНаСервере_УТ`, поиск характеристики
перед `Спр.Записать()`). Влияет на ЛЮБОЙ заказ с позициями, чьи характеристики уже
существуют, — не связано с прямой загрузкой.

**Обход (на стороне загрузчика, РЕШЕНО 06.09.2026):** при записи документа сразу
подставлять в строки `Характеристику` (найти существующую по владельцу+имени или
создать по формату «<обозначение>  <материал.НаименованиеДляПечати>») — тогда
оформление не создаёт характеристики само. Реализовано в
`tools/as_order_loader/build_execute_payload.py` (блок «Характеристика: найти
существующую или создать») и проверено end-to-end: заказ №000000861 (286 позиций,
прогон Шипиловского 06.09), ошибок 0. Подтверждено пользователем 06.09: 861
оформлен штатно через «Оформить заказ», цены посчитались — обход работает.
Баг поиска в форме 1С остаётся открытым для 1С-разработчика — обход лишь не
даёт ему проявиться.

### Цены/суммы не считаются при программном создании документа (05.09.2026)

Контекст: пилот создал `асСпецификацияЗаказа` №000000849 напрямую
(`СоздатьДокумент()` + заполнение ТЧ + `Записать()`). Цен нет — и это не баг пилота:

- Расчёт цены/суммы живёт **в модуле объекта обработки ввода/загрузки заказа**
  (дампы `docs/модуль ввод нового заказа.txt` и `docs/модуль загрузки с сайта.txt`):
  `РасчетФормул()` (площадь/масса изделия) → `УстановкаПрайсаНаСервере()`
  (цена из регистра `асЦеныПродукции` по типу: прямой участок/фасонка/нестандарт × КС/ПС)
  → сумма = цена × масса/площадь.
- У самого документа этих методов нет (проверено через MCP: «Метод объекта не
  обнаружен»). Автопересчёта при записи/проведении нет — заказы 845–847 не проведены,
  но с суммами, т.к. цены туда писала обработка.
- В 847 строка `1-1-2` (нерж труба Ø200, AISI 430 0.80) имеет Цена=0 — при том что
  цена в регистре для этого материала есть (ПрямойУчастокКС 3650). Штатный расчёт
  цены для этой позиции не сработал — похоже на баг/особенность обработки, не на
  ошибку XML.

**Вывод:** прямая загрузка документа без обработки не даст цен. Варианты:
а) после загрузки открывать заказ в обработке и жать «Расчёт» (ручной шаг);
б) вынести загрузку в метод той же обработки (EPF) — тогда штатный расчёт отработает
автоматически; в) реплицировать формулу расчёта — НЕ рекомендуется (зависимости от
припусков на замки, отходов, нестандарта).

**Статус:** НЕ РЕШЕНО. Рекомендуется вариант (б) — заодно закрывает вопрос безопасности
execute_code.

### Цены/суммы: РЕШЕНО через штатный проход обработки (05.09.2026)

Реализовано в `tools/as_order_loader/as_order_loader.bsl` (процедура `РассчитатьВсеСтроки`):
строки документа копируются в ТЧ `Заказы` обработки `асВводНовогоЗаказа` и одним вызовом
`РедактироватьВсеНаКлиенте_ДляИзмененныхВМодуле()` обсчитываются точно так же, как при
нажатии кнопки «Расчёт» (Расчеты_D → РасчетФормул → УстановкаПрайсаНаСервере →
РасчетЦен → РасчетЦеныЗаЕдиницу). Два реквизита, которые форма заполняет при открытии,
выставляются явно: `ТекущаяПрограмма1С = "КА"` и
`УчитыватьЗамкиВРасчетеПлощадиДляСчета = Истина` (S = Sclean + Slock).

Проверка: на 20 позициях заказа №000000851 программный расчёт дал идентичные
интерактивному значения S, типов цен и цен по всем строкам (end-to-end через
логику модуля — заказ 000000852, сверка пройдена, тестовые заказы 848–850 и 852
помечены на удаление; эталонный 851 сохранён).

Нюанс: «ПоЦенеИзделия» в документах 847/851 — это позиции БЕЗ металла
(цена составного соединения шина/УГФ), а не воздуховоды с материалом. Для строк
с материалом штатный тип — «ПрямойУчастокПС»/«ФасонныеИзделияПС» из регистра
`асЦеныПродукции`.

**Статус:** РЕШЕНО. Осталось собрать EPF по README (`tools/as_order_loader/`).

### Производные размеры фасонки: применять настройки продукции (решено в пилоте 05.09.2026)

Симптом: после «Расчёта» в обработке у шумоглушителей отрицательные S и Сумма.
Причина: для сложной фасонки (15-1-1, 15-2-1 и др.) площадь считается от производных
размеров (`a1`, `b1` — корпус; `d1` — корпус круглый; `p`, `p1` — ниппели), которые
в ручном вводе обработка выводит из регистра сведений `асНастройкиПродукции`
(Вариант1 = константа, Вариант2 = формула от зависимого параметра). Прямая загрузка
этих размеров не ставила → в формулах типа `Sring = a1*b1 − A*B` нули давали
отрицательную площадь.

Решение в пилоте (`/tmp/build_pilot_payload.py`): после заполнения базовых размеров
из спецификации применяем правила из `асНастройкиПродукции` к незаполненным (=0)
параметрам строки (Вариант1 и Вариант2; диапазонный Вариант3 пока не встречался).
Заказ №000000851: S положительные, производные размеры корректны
(15-2-1: a1=A0+100, b1=B0+100, p=p1=50; 15-1-1: d1=D0+100).

**Статус:** РЕШЕНО в пилоте. Для XML-пути 1С эти размеры тоже не выставляет — тот же
дефект проявится при наличии шумоглушителей в XML (в 847 их не было).

### Толщина металла: расхождения Python-пайплайна с КП завода (05.09.2026, сверка с КП №599 по проекту Шипиловский/ГБОУ №599)

**Статус: РЕШЕНО 05.09.2026** (правки `normalize_thickness`, КСД, блок-парсер PDF;
тесты `tests/test_techdept_rules.py`, `tests/test_pdf_spec_blocks.py`,
`tests/test_api.py::test_load_tables_from_pdf_block_fallback`).

Принятые решения (согласованы с пользователем):
1. Толщина НЕ указана в проекте («согласно СП 60») → точное значение из
   ГОСТ-таблицы техотдела (0.55/0.7/0.8/1.0), а не default 0.8.
2. Толщина указана в проекте явно → берётся как есть, ГОСТ-таблицей не
   перебивается (исправило 0.9→1.0 на пожарной защите).
3. КСД → толщина по таблице от макс. размера сечения (600x600 → 0.7).
4. ГОСТ-бланки с многострочными ячейками → fallback на разбор текстового слоя
   (`parse_spec_text_blocks` в pdf_spec_extractor.py; включение при <25%
   валидных строк таблиц — `api.load_tables_from_pdf`).

Исключения (не трогаем, помечены пользователем):
- Дымоудаление: заказчик сам просил поменять — исключение из правил.
- Противопожарные клапаны: то же.
- Сечение 1000 мм: КП завода даёт 0.70, правила техотдела требуют 0.8 —
  в коде по правилам техотдела (0.8), расхождение с этим КП зафиксировано.
- Зонт крышный Ф315: система t=0.55 (таблица по 315 мм), КП даёт 0.70 —
  вопрос к техотделу, открыто.

Прочее (актуально): противопожарные клапаны (ОКС-1 в КП, покупные с ценами)
пайплайн маппит на производственные артикулы 20-2/16-2-1 — уточнить у
техотдела, корректно ли. Полный прогон всего PDF без выбора страниц подмешивает
позиции оборудования из других разделов (NED-шумоглушители → 15-x) — для
чистого заказа грузить секции воздуховодов (стр. 25–28 в этом проекте) или

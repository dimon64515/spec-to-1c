# Спецификация маппинга JSON → 1С: документ `асСпецификацияЗаказа`

**Для кого:** 1С-разработчик базы «ВОК-Регион» (КА 2 / Softvent), который пишет
расширение конфигурации / HTTP-сервис, загружающий JSON-спецификацию заказа
в табличную часть «Товары» документа `Документ.асСпецификацияЗаказа`.

**Статус документа:** спецификация поведения. BSL-код здесь намеренно НЕ приводится —
он уже написан и проверен end-to-end в модуле обработки `асЗагрузкаЗаказаИзJSON`
(`tools/as_order_loader/as_order_loader.bsl`, заказы №000000852–000000860). Этот файл —
точное описание того, ЧТО и КУДА писать, чтобы повторить то же поведение в расширении.

**Источники истины:**
- поведение — `tools/as_order_loader/as_order_loader.bsl` (ЗаполнитьСтроку, УстановитьСоединение, ПрименитьНастройкиПродукции, РассчитатьВсеСтроки);
- типы и имена реквизитов — `reference/1c_meta_spec_doc.json` (метаданные документа);
- справочники — `reference/catalog_data.json`, `reference/ventilation_products_full.json`, `docs/README_1C_SPRAVOCHNIKI.md`;
- сборка входного JSON — `json_positions.py` (корень репозитория).

Пометки достоверности: **[подтверждено]** — есть проверка на живой базе или прямое подтверждение снимком метаданных; **[проверить в базе]** — типовая практика / вывод по аналогии, требует проверки на копии базы.

## 1. Общий контракт входного JSON

Тело POST-запроса (HTTP-сервис) — один JSON-объект:

```json
{
  "order_comment": "Задача Битрикс24 №42: Шипиловский — ОВ2",
  "request_id": "bitrix-task-42-msg-7",
  "positions": [
    {
      "article": "1-2-1",
      "qty": 6,
      "thickness": 0.8,
      "material": "Рулон оц.(08ПС)0.80",
      "shina": "95",
      "conn0": "6",
      "conn1": "6",
      "params": {"A0": 400, "B0": 200, "L0": 1250},
      "comment": "подъезд 2, этаж 3"
    }
  ]
}
```

### Ключи корня

| Ключ | Тип | Обязательность | Назначение |
|---|---|---|---|
| `order_comment` | строка | нет | Комментарий документа. Если пуст/отсутствует — дефолт «Загрузка из JSON» **[подтверждено — текущее поведение обработки]** |
| `request_id` | строка | нет | Идентификатор запроса. **Идемпотентность НЕ требуется: каждый POST создаёт НОВЫЙ документ.** Ключ может логироваться/дублироваться в комментарий, но поиска существующего документа по нему не делаем |
| `positions` | массив | **да** | Позиции заказа (см. ниже) |

### Элемент `positions[i]`

| Ключ | Тип | Обязательность | Назначение |
|---|---|---|---|
| `article` | строка | да | Артикул из `Справочник.асПродукция` (реквизит «Артикул»). Поиск: `НайтиПоРеквизиту("Артикул", ...)` |
| `qty` | число | да | Количество изделий |
| `thickness` | число | да | Толщина металла, мм (например 0.8) |
| `material` | строка | да | **Точное** наименование из `Справочник.асМатериалы`, толщина — два знака (`0.80`, не `0.8`). Поиск по наименованию, точное совпадение |
| `shina` | строка | да | Шина на соединение: `65` / `95` / `105`; пустая строка — без шины. Ключ всегда присутствует |
| `conn0` | строка | да | Код соединения на конце 0: `6` = «Шина / уголок», `2` = «Без соединения»; пустая строка — соединение не задавать |
| `conn1` | строка | да | То же для конца 1 |
| `params` | объект | нет | Размеры строки: имена ключей = имена числовых реквизитов ТЧ «Товары» (см. раздел 4). Неизвестные ключи — пропуск с предупреждением, не ошибка |
| `comment` | строка | нет | Произвольный комментарий к позиции |

Правило выбора шины (формирует Python-сторона, `json_positions.py::shina_by_max_dim`, правила техотдела):
максимальный габарит ≤350 мм → `65`; 400–950 → `95`; ≥1000 → `105`. Шина ставится только если хотя бы на одном конце соединение `6` **[подтверждено]**.

## 2. Шапка документа `асСпецификацияЗаказа`

Перечень реквизитов шапки — `reference/1c_meta_spec_doc.json`, ключ `data.Реквизиты`.

### Что заполняется программно при создании (по проверенной логике обработки)

| Реквизит | Тип (из метаданных) | Как заполняется | Примечание |
|---|---|---|---|
| `Дата` | Дата(ДатаВремя) | `ТекущаяДатаСеанса()` | **[подтверждено]** |
| `Комментарий` | Строка(0, Переменная) | `order_comment`, при пустом — «Загрузка из JSON» | **[подтверждено]** |
| `Номер` | Строка(9, Переменная) | автонумерация при `Записать()` | **[подтверждено]** |

### Реквизиты шапки, которые типовая форма/логика обычно требует заполненными — **[проверить в базе]**

Текущая внешняя обработка их **не заполняет** (заказы №000000852–000000860 созданы и обсчитаны без них), но при переносе в расширение стоит сверить, не требуют ли они значения по умолчанию для вашего сценария (проведение, печать, интеграции):

| Реквизит | Тип | Комментарий |
|---|---|---|
| `Организация` | СправочникСсылка.Организации | Одна организация в базе — заполняется типовыми механизмами; при программном создании, вероятно, пусто, пока не понадобится проведение. **Проверить в базе** |
| `Контрагент` / `Партнер` / `Соглашение` | справочники КА | Для «черновика спецификации из проекта» не нужны (заказ ещё не продажа). **Проверить в базе**, нужны ли для отчётов/печати |
| `СтатусСпецификации` | ПеречислениеСсылка.асСтатусыСпецификаций | При пустом значении документ остаётся «новым». **Проверить в базе**: нет ли обязательной инициализации статуса (например «Новая») — в текущей обработке не заполняется |
| `Менеджер` / `Ответственный` | СправочникСсылка.Пользователи | Типовые документы заполняют ответственного; при вызове из HTTP-сервиса это будет сервисный пользователь. **Проверить в базе** |
| `СуммаДокумента` | Число(15,2) | Пересчитывается обработкой `асВводНовогоЗаказа` вместе со строками? Суммы по строкам считаются в ТЧ; итог шапки — **проверить в базе** |
| `ТекущаяПрограмма1С` | Строка(50) | В шапке документа есть такой реквизит; обработка расчёта выставляет свой одноимённый реквизит обработки = `"КА"`. Заполнение реквизита **документа** текущая логика не делает — **проверить в базе**, не влияет ли он на печатные формы |

Документ создаётся и записывается **без проведения** (`Записать()`, не `Записать(РежимЗаписиДокумента.Проведение)`) **[подтверждено]**.

## 3. ТЧ «Товары»: маппинг полей JSON на реквизиты

Метаданные: `reference/1c_meta_spec_doc.json` → `data.ТабличныеЧасти[Имя="Товары"].Реквизиты` (184 реквизита). Ниже — только те, что участвуют в загрузке.

### 3.1. Идентификация продукта и служебные строки

| JSON | Реквизит ТЧ | Тип реквизита | Правило заполнения |
|---|---|---|---|
| `article` | `Продукт` | СправочникСсылка.Номенклатура, СправочникСсылка.асПродукция | Ссылка на `асПродукция`, поиск по реквизиту «Артикул». **Обязательно Продукт, не Номенклатура!** Не найден → ошибка «Строка N: не найден продукт…» |
| — (из найденного продукта) | `Номенклатура` | СправочникСсылка.Номенклатура | `Продукт.Продукт` (реквизит справочника `асПродукция`) |
| `article` | `АртикулПродукции` | Строка(15) | Как в JSON |
| — (вычисляется) | `АртикулГруппы` | Строка(2) | Часть `article` до первого дефиса (`"1-2-1"` → `"1"`); если дефиса нет — весь артикул |
| — (из продукта) | `ГруппаПродукцииСтр` | СправочникСсылка.асГруппыПродукции | `Продукт.ГруппаПродукции` |
| — (из продукта) | `СечениеСтр` | ПеречислениеСсылка.асВидыСечений | `Продукт.ВидСечения` |
| `qty` | `n` | Число(10,3) | Количество |
| `qty` | `np` | Число(10,3) | То же количество (количество к производству) |
| `thickness` | `t` | Строка(10)/Число(10,2) | Толщина, числом |
| `thickness` | `t2` | Число(5,2) | То же значение |
| `material` | `Материал` | СправочникСсылка.асМатериалы | `асМатериалы.НайтиПоНаименованию(имя, Истина)` — точное совпадение, два знака толщины. Не найден → ошибка |
| — | `Материал2` | СправочникСсылка.асМатериалы | = `Материал` |
| `comment` | `КомментарийКПродукцииИзOnLine` | Строка(200) | Как в JSON |

### 3.2. Шина на соединение

| JSON | Реквизит ТЧ | Тип | Правило |
|---|---|---|---|
| `shina` | `МатериалНаСоединение0` | СправочникСсылка.асПродукция, СправочникСсылка.асМатериалы | Ссылка на элемент `асПродукция` (шины лежат там, группа «Соединение»), поиск по точному наименованию |
| `shina` | `МатериалНаСоединение1` | то же | То же значение, что и для конца 0 |

Сопоставление кода шины → наименование **[подтверждено — BSL обработки]**:

| `shina` | Материал оцинкованный | Материал с «нерж» в имени |
|---|---|---|
| `65` | `Шина 20 / УГФ 65` | `Шина 20(нерж.430) / УГФ 65(нерж.430)` |
| `95` | `Шина 20 / УГФ 95` | `Шина 20 / УГФ 95` |
| `105` | `Шина 30 / УГФ 105` | `Шина 30 / УГФ 105` |

Пустая `shina` → реквизиты не заполняются. Не найдена шина → ошибка строки. Полный перечень — `docs/README_1C_SPRAVOCHNIKI.md`.

### 3.3. Соединения

| JSON | Реквизит ТЧ | Тип | Правило |
|---|---|---|---|
| `conn0` | `СоединениеВоздуховода_c0` | СправочникСсылка.асСоединениеВоздуховодов | Код → наименование → `НайтиПоНаименованию(..., Истина)` |
| `conn1` | `СоединениеВоздуховода_c1` | то же | аналогично |

Коды **[подтверждено]**: `6` → «Шина / уголок», `2` → «Без соединения». Пустая строка → реквизит не заполняется. Неизвестный код → ошибка строки. Полный список соединений (19 шт., с учётом вида сечения: круглое/прямоугольное) — `reference/catalog_data.json` (ключ `connections`) и `docs/README_1C_SPRAVOCHNIKI.md`, здесь не дублируется.

## 4. Раздел `params`: параметры-реквизиты ТЧ «Товары»

### 4.1. Полный перечень числовых реквизитов размеров (из метаданных ТЧ «Товары»)

Все — `Число(10, 0)` (некоторые «Неотрицательный»), ключи JSON `params` совпадают с именами реквизитов один-в-один **[подтверждено по метаданным 08.09.2026]**:

| Геометрия | Реквизиты |
|---|---|
| Прямоугольные габариты | `A0`, `B0`, `a1`, `a2`, `a3`, `b1`, `b2`, `b3` (а также `a4`, `a5`, `b4`, `b5` — строка/число) |
| Круглые габариты | `D0`, `d1`, `d2`, `d3`, `d4` |
| Длины | `L0`, `l1`, `l2`, `l3`, `l4`, `l5`, `l6` |
| Углы | `u`, `u1`, `u2` |
| Радиусы | `R`, `R1`, `R2`, `R3` |
| Прочее | `p`, `p1`, `p2`, `p3` |

**Переименования из пайплайна** (`json_positions.py`, словарь `_PARAM_KEY_1C = {"U0": "u", "R0": "R", "P0": "p"}`): внутренние имена `U0`/`R0`/`P0` извлечения PDF → в JSON и далее в реквизиты идут как `u`/`R`/`p` **[подтверждено]**.

Прочие числовые реквизиты ТЧ, которые НЕ приходят из JSON (считает 1С): `n`, `np`, `t`, `t2`, `S`, `M`, `Slock`, `Sclean`, `Lclean`, `V`, `L_Izd`, `Цена`, `ЦенаЕд`, `Сумма`, `Отход`, `ОтходПроцент`, `S_Соединения0..3`, `M_Соединения0..3`, `Диаметр_c0..c3`, `Диаметр_r0..r3` и т.д. — их из `params` не писать (только через расчёт, см. раздел 6).

### 4.2. Применимость ключей `params` к группам продукции

Твёрдо подтверждено снимками базы (см. `reference/catalog_data.json` → `product_parameters`, и строки эталонного заказа `reference_order_000000839`):

| Артикул / продукт | Вид сечения | Применимые ключи `params` | Достоверность |
|---|---|---|---|
| `1-1-1`, `1-1-2` — воздуховод круглого сечения (прямошовный / спирально-навивной) | Круглое | `D0`, `L0` (соединения — через `conn0`/`conn1` → `СоединениеВоздуховода_c0/c1`) | **[подтверждено]** |
| `1-2-1` — воздуховод прямоугольного сечения | Прямоугольное | `A0`, `B0`, `L0` (соединения — `СоединениеВоздуховода_r0/r1`, из `product_parameters`; в текущем контракте передаются те же `conn0/conn1`) | **[подтверждено]** (для A0/B0/L0) |
| `12-1-3` — Фланец (кр) | Круглое | `D0`, `p` (число отверстий) | **[подтверждено]** |
| `2-2-2` — Отвод (прямоуг.) | Прямоугольное | `A0`, `B0`, `u` (угол поворота), `R` (радиус) — по строке заказа 839: `100x100-90-100-100` | **[подтверждено]** для A0/B0/u; `R` — **[проверить в базе]** для прямоугольных отводов |
| `3-1-1` — Переход (круглое→круглое) | Круглое/Переходное | `D0`, `d1`, `L0` — по строке 839: `Ф100/Ф100-111` | **[подтверждено]** для D0/d1/L0; для прямоугольных переходов — `A0`, `B0`, `a1`, `b1` (+`L0`) **[проверить в базе]** |
| Отводы круглого сечения (группа «Отвод», артикулы `2-1-*`) | Круглое | `D0`, `u` (угол), `R` (радиус изгиба), `L0` | **[проверить в базе]** — типовая практика, совпадает с именами реквизитов и `асНастройкиПродукции` |
| Тройники (`4-*`), крестовины (`5-*`), врезки (`7-*`) | Круглое/Прямоуг./Переходное | Сечения патрубков: круглые → `D0`, `d1`, `d2`; прямоугольные → `A0`, `B0`, `a1`…; переходные — смесь `D0`/`A0`/`B0` | **[проверить в базе]** (состав индексов по патрубкам смотреть в `асНастройкиПродукции` и строках-примерах) |
| Зонты вытяжные/крышные, КСД | Прямоуг./Переходное | `A0`, `B0` (сборка), `d1` (выход), `L0`, `H`-подобные длины через `l1`…`l6` | **[проверить в базе]** |
| Заглушки (`8-*`) | Круглое/Прямоуг. | `D0` или `A0`, `B0` | **[проверить в базе]** |
| Утки, мягкие вставки, муфты, шиберы | Круглое/Прямоуг. | Сечение сечениями (`D0`/`A0`/`B0`) + длины `L0`/`l1` | **[проверить в базе]** |
| Шумоглушители | Круглое/Прямоуг. | Сечение + `L0`; производные `a1`, `b1`, `d1` — из регистра `асНастройкиПродукции` (см. раздел 6) | **[подтверждено]**, что производные размеры обязательны (без них площадь уходит в минус) |

Общее правило: какие реквизиты реально участвуют в расчёте конкретного продукта, видно в регистре `асНастройкиПродукции` (измерение «Продукт», ресурсы: ПараметрПродукции, Вариант, КонстантаЗначения, ЗависимыйПараметр, Оператор, ЧислоX — см. `reference/РегистрСведений_асНастройкиПродукции.json`, `reference/product_settings_meta.json`) — это и есть список параметров, которые 1С ждёт заполненными для данного продукта.

**Правило применения `params`:** каждый ключ пишется напрямую в одноимённый реквизит строки; если реквизита с таким именем в ТЧ нет — ключ пропускается с предупреждением «параметр не применён» (не ошибка). Значения, уже заданные спецификацией, регистром `асНастройкиПродукции` **не перезаписываются** (перезаписываются только нулевые) **[подтверждено]**.

## 6. Алгоритм после заполнения строк

Порядок обязателен — он обеспечивает паритет с интерактивным вводом через обработку `асВводНовогоЗаказа` (проверен на заказах №000000849–000000860, 286 позиций) **[подтверждено]**:

1. **Заполнить все строки ТЧ** по разделам 3–4 (внутри одной транзакции с созданием документа).
2. **ПрименитьНастройкиПродукции** — для каждой строки выбрать из регистра сведений `асНастройкиПродукции` все записи по измерению «Продукт». Для каждой записи:
   - имя целевого реквизита = строковое представление «ПараметрПродукции» (реквизита ТЧ нет — пропуск);
   - если реквизит уже не равен 0 (задан спецификацией) — не трогать;
   - Вариант «Вариант1» → записать «КонстантаЗначения»;
   - Вариант «Вариант2» → вычислить от «ЗависимыйПараметр» по «Оператор» (асАрифметическиеОператоры: сложение/вычитание/умножение/деление на «ЧислоX»; деление на 0 → 0).
   Этот шаг обязателен: без производных размеров (a1, b1, d1, p, …) у фасонки (шумоглушители и др.) расчёт площади уходит в минус **[подтверждено]**.
3. **РассчитатьВсеСтроки** — единый расчёт площадей/масс/цен по всем строкам сразу (ровно то, что делает кнопка «Расчёт»):
   - создать обработку `Обработки.асВводНовогоЗаказа.Создать()`;
   - `ДатаУстановкиЦен = ТекущаяДатаСеанса()`;
   - `ТекущаяПрограмма1С = "КА"` — конфигурация базы (Комплексная автоматизация); без этого расчёт расходится с интерактивным. При переходе базы на УТ/УНФ/БП — поменять значение;
   - `УчитыватьЗамкиВРасчетеПлощадиДляСчета = Истина` — S = Sclean + Slock; без этого площадь занижается на площадь замков, цена за изделие — пропорционально;
   - перенести строки документа в ТЧ «Заказы» обработки (только общие колонки), поставить `ТребуетсяПересчет = Истина`;
   - вызвать `О.РедактироватьВсеНаКлиенте_ДляИзмененныхВМодуле()`;
   - вернуть результаты обратно в строки документа (по общим колонкам);
   - для строк с `ЦенаЕд = 0` — предупреждение «цена 0 — проверьте прайс (тип цены …)» (не ошибка; известный кейс — незаполненная колонка «СпиральноНавивной» в `асЦеныПродукции` для AISI 430).
4. **Записать документ** и зафиксировать транзакцию. Исключение → отменить транзакцию, вернуть ошибку.

**Идемпотентность:** не реализуется. Каждый POST создаёт новый документ, даже с повторным `request_id`. Бот ретраит при таймауте — дубликат маловероятен (286 позиций пишутся ~14 с при таймауте 280 с); если появится проблема — решать на стороне middleware/бота.

## 7. Ответ сервиса

Успех (HTTP 200), структура как у `ЗагрузитьЗаказ` **[подтверждено]**:

```json
{
  "Успех": true,
  "НомерЗаказа": "000000860",
  "КоличествоСтрок": 286,
  "Ошибки": [],
  "Предупреждения": ["Строка 1 (1-2-1): цена 0 — проверьте прайс (тип цены \"...\")"]
}
```

| Поле | Тип | Наполнение |
|---|---|---|
| `Успех` | Булево | `Истина`, если ошибок нет |
| `НомерЗаказа` | Строка | Номер записанного документа (`"000000852"`); при неудаче — пустая строка |
| `КоличествоСтрок` | Число | `Документ.Товары.Количество()` |
| `Ошибки` | Массив строк | «Разбор JSON: …», «не найден продукт/материал/шина/соединение», «Запись документа: …». Формат: `Строка N: …` |
| `Предупреждения` | Массив строк | Параметр не применён, цена 0, расчёт недоступен и т.п. |

Бизнес-ошибки (не найден артикул и т.п.) — **не исключения**: документ создаётся, ошибки перечисляются в `Ошибки`/`Предупреждения` при HTTP 200. Исключение платформы/невалидный JSON — HTTP 500 с `{"Успех": false, "НомерЗаказа": null, "Ошибки": ["<ОписаниеОшибки>"], "Предупреждения": []}`. Кодировка UTF-8, `Content-Type: application/json`.

## 8. Права сервисной учётной записи (минимум)

Документ `асСпецификацияЗаказа` (добавление/запись), справочники `асПродукция`, `асМатериалы`, `асСоединениеВоздуховодов`, `асГруппыПродукции`, перечисление `асВидыСечений`, регистр сведений `асНастройкиПродукции`, обработка `асВводНовогоЗаказа` (включая её вызов из программного кода), справочник `асАрифметическиеОператоры` (чтение). Расширенный список и требования к аутентификации (`X-API-Key`) — в `docs/ТЗ_HTTP_СЕРВИС_ЗАГРУЗКА_ЗАКАЗА_1С.md`.

## Резюме для разработчика: что проверить в живой базе

1. **Шапка:** нужно ли программно заполнять `Организация`, `СтатусСпецификации`, `Менеджер`/`Ответственный`, `СуммаДокумента` — текущая обработка их не трогает, но для полноценного документа они могут понадобиться (см. раздел 2).
2. **Поиск соединений:** `НайтиПоНаименованию("Шина / уголок")` может вернуть карточку круглого сечения для прямоугольного воздуховода — на копии базы проверить, что расчёт не зависит от вида сечения соединения, либо добавить отбор.
3. **Применимость params** по группам (раздел 4.2): подтверждена только для воздуховодов 1-1-1/1-1-2/1-2-1, фланца 12-1-3 и частично отводов/переходов по заказу 839; остальные группы (тройники, зонты, КСД, заглушки и пр.) — сверить с `асНастройкиПродукции` и реальными строками заказов.
4. **Незаполненные прайсы:** AISI 430 спирально-навивной грузится с ценой 0 + предупреждение (вопрос к техотделу, см. `docs/BACKLOG.md`).
5. **Платформа:** HTTP-сервисы в расширениях — платформа 8.3.11+, проверить версию публикации.

Остальное (маппинг ТЧ, шины, материалы, производные размеры, расчёт цен, формат ответа) — подтверждено прогонами на живой базе и может быть перенесено в расширение без изменений.
